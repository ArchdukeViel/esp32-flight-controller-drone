================================================================================
0. BLUNT EXECUTIVE JUDGMENT
================================================================================

This hardware is usable for learning, bench validation, sensor work, PID
experiments, motor-output experiments, and eventually a cautious tethered/low
hover test.

This hardware is NOT a production flight controller. The ESP32 DevKit V1 is a
soft real-time board with WiFi/Bluetooth stacks, I2C sensors, and awkward
physical mounting. The MPU6050 has no magnetometer. The BMP280 is useful for
slow altitude telemetry, not fast altitude hold. The ESC/motor combination is
fine for a 450 mm class quad, but power is not the hard part. Timing, safety,
state control, and testing discipline are the hard parts.

Recommendation:
  Build this as a staged experimental flight-controller laboratory. Do not jump
  to free flight. Do not jump to WiFi joystick control. Do not install props
  until the pre-propeller review says every gate has passed.

Android WiFi control recommendation:
  Use the Android app first for telemetry, calibration, PID tuning, and motor
  test commands while motors are disabled or no-prop. Only after the full
  no-prop integration passes should WiFi command input be tested as an
  experimental control source. Active WiFi flight control must use UDP packets,
  a dead-man switch, packet watchdog, sequence numbers, CRC, local ESP32 AP mode,
  and immediate motor cutoff on packet loss. Even then: tethered testing only
  before any real hover attempt.

Strategic rule:
  The app must never be the only safety system. The firmware safety state
  machine owns safety. The Android app merely requests commands. Requests are
  disposable. Safety is law.

================================================================================
1. TECHNICAL CORRECTIONS APPLIED
================================================================================

These corrections override the original Claude and DeepSeek documents.

1. MPU6050 WHO_AM_I
-------------------
Correct expected value:
  MPU6050 WHO_AM_I register expected value = 0x68

Implementation rule:
  If WHO_AM_I is not 0x68, do not silently continue. Log the actual value and
  identify whether the connected sensor is a different MPU/ICM variant.

2. BMP280 chip ID
-----------------
Correct expected value:
  BMP280 chip ID register expected value = 0x58

Implementation rule:
  If chip ID is 0x60, the board is likely BME280 or another Bosch environmental
  sensor variant, not BMP280. Do not pretend it is BMP280 unless the driver
  explicitly supports the detected device.

3. ESP32 MCPWM hardware
-----------------------
Correct assumption for classic ESP32 DevKit V1:
  The ESP32 has enough MCPWM resources for four ESC outputs. Use the ESP-IDF
  MCPWM driver and do not copy any claim that classic ESP32 has three MCPWM
  modules. Treat MCPWM resource allocation as board-specific and verify during
  driver implementation.

4. Receiver input
-----------------
Use RMT as the primary receiver PWM capture method if an RC receiver is used.
GPIO edge interrupt capture is fallback only.

5. ESP-IDF version
------------------
This project targets ESP-IDF v6.0.1.
Toolchain path: C:\Akmal\Project-tools\.espressif\v6.0.1\esp-idf

Note: ESP-IDF v6 uses the new-style i2c_master API (handle-based:
i2c_master_bus_handle_t, i2c_device_handle_t). Do not use legacy
i2c_param_config / i2c_driver_install patterns from v4/v5 examples.
All driver implementations must use the v6 API.

6. Motor numbering convention
-----------------------------
This project uses ONE convention everywhere:

           FRONT
      M1           M2
   front-left   front-right
       \          /
        \        /
         \      /
          \    /
          /    \
         /      \
        /        \
       /          \
      M4           M3
   rear-left    rear-right
            REAR

Default rotation convention, viewed from above:
  M1 front-left  = CCW
  M2 front-right = CW
  M3 rear-right  = CCW
  M4 rear-left   = CW

Every firmware log, motor test command, mixer equation, README diagram, and
Android app UI must use this exact convention.

================================================================================
2. NON-NEGOTIABLE SAFETY RULES
================================================================================

1. Propellers are forbidden until pre-propeller readiness is signed off.
2. Motor power is forbidden until ESC output has been measured on a logic
   analyzer or oscilloscope.
3. MCPWM outputs must initialize to 1000 us before any motor/ESC task runs.
4. Emergency stop must be implemented before any motor spin test.
5. Every motor test must require explicit no-prop confirmation.
6. Arming requires explicit user action plus pre-arm checks.
7. App command packets are never trusted blindly.
8. Any stale input source means throttle forced to zero and motors to 1000 us.
9. Any persistent IMU fault means FAILSAFE or ERROR_LOCKOUT.
10. BMP280 failure is not flight-critical for attitude mode.
11. WiFi tuning/config mode and real motor control are separated by state.
12. If active WiFi command mode is later enabled, it must be treated as
    experimental and must run through stricter failsafe testing than RC input.

3. RECOMMENDED FIRMWARE STACK
================================================================================

Language:
  C++17 using ESP-IDF C APIs.

C++ constraints:
  - No exceptions in embedded path.
  - No RTTI.
  - No heap allocation inside the control loop.
  - No STL containers in the real-time path unless statically allocated and
    proven harmless.
  - Use plain structs for telemetry and inter-module data.
  - Use classes only where they improve encapsulation: PID, estimator,
    state machine, driver wrappers.

ESP-IDF components:
  - board_config
  - i2c_bus
  - mpu6050
  - bmp280
  - calibration
  - estimation
  - input
  - wifi_control
  - control
  - motor_output
  - safety
  - telemetry
  - config_nvs
  - diagnostics
  - tests

Core split:
  Core 1: flight control, IMU read, estimator, PID, mixer, MCPWM command,
          safety checks.
  Core 0: WiFi, HTTP server, UDP command receiver, telemetry streaming, NVS,
          diagnostics, low-priority commands.

Task model, initial target:

  Task                       Core  Priority   Period / trigger
  -------------------------------------------------------------------------
  control_task                  1      high   250 Hz, timer-driven
  imu_task                      1      high   250 Hz, synchronized with control
  safety_task                   1      high   100 Hz
  motor_output_task             1      high   250 Hz or direct from control_task
  baro_task                     0      low    10-25 Hz
  wifi_udp_rx_task              0      med    packet-driven, active only in WiFi modes
  wifi_http_task                0      low    config/tuning only, disabled in active control
  telemetry_task                0      low    20-50 Hz
  diagnostics_task              0      low    1 Hz
  config_task                   0      low    on demand

Control-loop initial rate:
  250 Hz / 4000 us period.

Why not 500 Hz first:
  A beginner ESP-IDF flight controller with I2C sensors, WiFi experiments, and
  old hardware needs boring success before heroic timing. Start at 250 Hz.
  Optimize later only after logs prove timing margin.

5. BOARD CONFIGURATION BASELINE
================================================================================

Default pins are suggestions. Verify against actual wiring before build.

I2C:
  SDA = GPIO21
  SCL = GPIO22
  Clock = 400 kHz

MPU6050:
  Address = 0x68 if AD0 low
  WHO_AM_I = 0x68

BMP280:
  Address = 0x76 or 0x77 depending on SDO
  Chip ID = 0x58

ESC/MCPWM suggested pins:
  M1 = GPIO18
  M2 = GPIO19
  M3 = GPIO23
  M4 = GPIO25

WiFi status / safety indicators:
  LED_STATUS = GPIO2 if available
  Optional buzzer = spare GPIO if available

Optional receiver pins if RC receiver is added:
  CH1 roll     = GPIO34 input-only
  CH2 pitch    = GPIO35 input-only
  CH3 throttle = GPIO32
  CH4 yaw      = GPIO33
  CH5 arm      = GPIO26
  CH6 mode     = GPIO27

Physical safety recommendation:
  Add a real mechanical power disconnect for ESC/battery power. Software is not
  a kill switch. Software is a polite suggestion sent through silicon.

================================================================================
7. SENSOR DESIGN
================================================================================

7.1 I2C bus
-----------
Use ESP-IDF i2c_master APIs. Provide:
  - init
  - scan
  - read register
  - write register
  - burst read
  - bus mutex
  - timeout on every transaction

Never block forever on I2C. A hung sensor must become a fault, not a frozen
flight controller.

7.2 MPU6050
-----------
Initialization:
  1. Wake sensor from sleep.
  2. Select stable clock source.
  3. Configure DLPF.
  4. Configure gyro range.
  5. Configure accelerometer range.
  6. Read WHO_AM_I and require 0x68.
  7. Read burst sample from 0x3B, 14 bytes.

Recommended initial ranges:
  Gyro = +/-500 deg/s, scale = 65.5 LSB/(deg/s)
  Accel = +/-4 g, scale = 8192 LSB/g
  DLPF = about 42/43 Hz class setting

Calibration:
  - Board still.
  - Collect 500-2000 samples.
  - Compute gyro bias.
  - Compute accelerometer bias; Z axis expects +1 g depending on orientation.
  - Save to NVS.
  - Validate on boot.

7.3 BMP280
----------
Initialization:
  1. Reset.
  2. Read chip ID and require 0x58.
  3. Read calibration coefficients.
  4. Configure oversampling and IIR filtering.
  5. Read compensated pressure and temperature.
  6. Compute relative altitude from ground pressure baseline.

Important:
  BMP280 is not in the fast control loop. It runs at 10-25 Hz and is used for
  telemetry and future slow altitude experiments only.

7.4 Sensor-only pass criteria
-----------------------------
PASS when:
  - I2C scan shows MPU6050 at 0x68.
  - MPU6050 WHO_AM_I = 0x68.
  - BMP280 detected at 0x76/0x77 if installed.
  - BMP280 chip ID = 0x58.
  - MPU6050 raw values change plausibly when tilted.
  - Calibrated gyro near zero while stationary.
  - Accel magnitude near 1 g while stationary.
  - BMP280 pressure plausible.
  - CSV telemetry is stable for at least 30 minutes before moving on.

================================================================================
8. ATTITUDE ESTIMATION
================================================================================

Initial estimator:
  Complementary filter for roll and pitch.

Formula:
  roll_accel  = atan2(ay, az) * RAD_TO_DEG
  pitch_accel = atan2(-ax, sqrt(ay*ay + az*az)) * RAD_TO_DEG

  roll  = alpha * (roll  + gx * dt) + (1-alpha) * roll_accel
  pitch = alpha * (pitch + gy * dt) + (1-alpha) * pitch_accel

Initial alpha:
  0.98

Yaw:
  No absolute yaw angle because there is no magnetometer. Only yaw rate control
  using gyro Z is allowed.

Accel magnitude gate:
  If accel magnitude is outside plausible range, skip accel correction that
  cycle and use gyro integration only.

Pass criteria:
  - Roll/pitch near 0 deg on level table.
  - Roll/pitch track a 30-45 deg manual tilt.
  - Stationary drift is acceptable over 5 minutes.
  - No estimator blow-up during quick hand movements.

================================================================================
9. CONTROL INPUT SOURCES
================================================================================

Input source priority:
  1. Emergency stop always wins.
  2. Physical disarm / failsafe always wins.
  3. RC receiver input if valid and selected.
  4. WiFi command input if valid and selected in WiFi-control mode.
  5. Stub input only for bench tests.

9.1 RC receiver input
---------------------
Use RMT as primary PWM capture if RC receiver is connected.

Receiver channels:
  Roll     1000-2000 us, center 1500
  Pitch    1000-2000 us, center 1500
  Throttle 1000-2000 us, low 1000
  Yaw      1000-2000 us, center 1500
  Arm      low/high switch
  Mode     optional

Failsafe:
  If no valid pulse for 100 ms, receiver invalid. Force throttle to zero,
  disarm, and enter FAILSAFE if armed.

9.2 Stub input
--------------
Use only for bench testing:
  throttle = 0
  roll = 0
  pitch = 0
  yaw = 0
  arm = false

Stub input must not be allowed to arm normal active flight mode.

9.3 WiFi Android command input
------------------------------
WiFi control is added as a separate input module, not hacked into receiver code.
The module outputs the same ControlInput struct used by RC/stub input.

Phases:
  Phase A: WiFi telemetry/config only, motors disabled.
  Phase B: WiFi motor-test command, no props, capped throttle.
  Phase C: WiFi command input dry-run, motors forced 1000 us.
  Phase D: WiFi no-prop active control, motors capped low.
  Phase E: WiFi tethered hover test only after full pre-prop review.

Do not start with WiFi active flight. That is how projects become shrapnel poetry.

================================================================================
10. WIFI ANDROID CONTROL ARCHITECTURE
================================================================================

10.1 Recommended user-facing approach
-------------------------------------
Build two interfaces, not one overloaded monster:

1. ESP32-hosted web UI, used from Android browser:
   - easiest for first implementation
   - no Android install needed
   - good for telemetry, calibration, PID settings, sensor checks
   - not recommended for active joystick control

2. Native Android app, Kotlin + Jetpack Compose:
   - used later for low-latency UDP command packets
   - has real joystick UI, dead-man button, emergency stop button
   - can maintain packet rate and connection state more cleanly

Avoid React Native/Expo for the control-link phase unless you are comfortable
with native UDP modules. Flutter is possible, but native Kotlin is more direct.

10.2 ESP32 WiFi modes
---------------------
Use SoftAP mode first:
  SSID: ESP32_FC_SETUP or ESP32_FC_CONTROL
  Static IP: 192.168.4.1
  App/phone connects directly to ESP32.

Reasons:
  - no router dependency
  - predictable IP
  - no internet needed
  - fewer moving parts

Disable WiFi power save in control experiments.

10.3 HTTP config server, DISARMED only
--------------------------------------
HTTP server is only for DISARMED configuration:

GET  /status
GET  /telemetry/latest
GET  /config
POST /calibrate/imu
POST /calibrate/baro_baseline
GET  /pid
POST /pid
POST /pid/save
POST /pid/defaults
POST /motor_test/prepare
POST /motor_test/start
POST /motor_test/stop
POST /estop

Hard rules:
  - HTTP server must not run during ACTIVE_STABILIZE.
  - HTTP motor-test commands require NO_PROP confirmation.
  - HTTP cannot bypass safety state machine.
  - HTTP cannot arm real flight mode.

10.4 UDP command protocol for Android control
---------------------------------------------
Use UDP for active command input, not HTTP.

UDP command packet rate:
  50 Hz from Android app to ESP32.

Firmware behavior:
  - If no valid packet for 150 ms: force throttle zero and disarm/failsafe.
  - If packet sequence stalls or repeats too often: input invalid.
  - If CRC fails: packet ignored.
  - If deadman is false: throttle forced zero.
  - If estop is true: immediate emergency stop.

Packet format, version 1:

struct WifiControlPacketV1 {
  uint8_t  magic0;        // 'F'
  uint8_t  magic1;        // 'C'
  uint8_t  version;       // 1
  uint8_t  flags;         // bit0 deadman, bit1 arm_req, bit2 disarm_req, bit3 estop
  uint32_t sequence;
  uint32_t app_time_ms;
  int16_t  roll;          // -1000..1000
  int16_t  pitch;         // -1000..1000
  int16_t  yaw;           // -1000..1000
  uint16_t throttle;      // 0..1000
  uint16_t crc16;
};

Mapping:
  roll      = packet.roll / 1000.0
  pitch     = packet.pitch / 1000.0
  yaw       = packet.yaw / 1000.0
  throttle  = packet.throttle / 1000.0

Initial throttle cap for WiFi experiments:
  Dry run: 0.0, motor output forced to 1000 us.
  No-prop motor response: <= 0.10 normalized.
  Tethered prop test: conservative cap decided only after pre-prop review.

10.5 Telemetry from ESP32 to Android
------------------------------------
Use UDP broadcast or unicast telemetry at 10-20 Hz for app display.
Use UART CSV as the canonical debug log during early phases.

Telemetry fields:
  - state
  - armed flag
  - failsafe reason
  - loop time
  - missed deadlines
  - WiFi packet age
  - WiFi RSSI
  - roll/pitch/yaw_rate
  - throttle command
  - motor outputs
  - sensor health
  - battery voltage if available

10.6 Android app UI requirements
--------------------------------
Minimum screen:
  - Connection status
  - Current safety state
  - Big red ESTOP button
  - Dead-man hold button
  - Arm/disarm controls with long-press confirmation
  - Throttle slider/stick with spring-to-zero for early test modes
  - Roll/pitch joystick
  - Yaw slider/stick
  - Sensor health indicators
  - Packet rate indicator
  - Last telemetry age
  - Motor outputs display

App behavior:
  - If app goes to background: send disarm/estop packet for 500 ms, then stop.
  - If screen locks: send disarm/estop.
  - If dead-man released: throttle zero.
  - If telemetry stale: warn and force command packets to disarm.
  - App must not remember armed state across restart.
  - App must boot into DISARMED UI every time.

10.7 WiFi active-control restrictions
-------------------------------------
Active WiFi command mode is allowed only if:
  - Sensors pass.
  - Calibration valid.
  - Loop timing clean.
  - UDP packet input is stable for 30 minutes in dry-run.
  - Failsafe packet-loss tests pass.
  - Emergency stop works.
  - No-prop motor response tests pass.
  - Pre-prop review explicitly approves WiFi mode.

WiFi active-control mode disables:
  - HTTP config server
  - PID save operations
  - heavy logging
  - OTA updates
  - Bluetooth
  - any blocking NVS writes

================================================================================
11. PID CONTROL DESIGN
================================================================================

Architecture:
  Cascaded angle -> rate PID for roll and pitch.
  Rate-only PID for yaw.

Outer angle loop:
  desired_angle - estimated_angle -> desired_rate

Inner rate loop:
  desired_rate - measured_rate -> motor correction

Initial target rates:
  Control update: 250 Hz.
  Angle and rate loops both run at 250 Hz initially for simplicity.
  Later optimization may run rate at 500 Hz if logs prove timing margin.

PID requirements:
  - anti-windup
  - derivative filtering or derivative-on-measurement
  - output clamping
  - integrator reset on disarm
  - PID output zero when not armed
  - PID output zero when IMU invalid
  - PID bypassed in motor test mode
  - throttle attenuation at low throttle

Conservative starting gains:
  These are only bench defaults, not flight guarantees.

  Angle roll/pitch:
    P = 3.0 to 4.0
    I = 0.02 to 0.08
    D = 0.0 initially
    output limit = +/- 200 deg/s desired rate

  Rate roll/pitch:
    P = 0.5 to 1.5
    I = 0.01 to 0.5
    D = 0.0 initially
    output limit = +/- 400 us correction

  Yaw rate:
    P = 1.0 to 3.0
    I = 0.0 to 0.05
    D = 0.0

Tuning order:
  1. Rate roll.
  2. Rate pitch.
  3. Yaw rate.
  4. Angle roll/pitch.
  5. Altitude hold not implemented until attitude control is stable.

================================================================================
12. MOTOR MIXING DESIGN
================================================================================

Motor layout convention:

           FRONT
        M1       M2
       CCW       CW
          \     /
           \   /
            \ /
            / \
           /   \
          /     \
        M4       M3
        CW       CCW
           REAR

Use one mixer equation family. The exact signs must be verified with the motor
response test. Initial convention:

  m1 = throttle + pitch - roll - yaw
  m2 = throttle + pitch + roll + yaw
  m3 = throttle - pitch + roll - yaw
  m4 = throttle - pitch - roll + yaw

Important:
  Mixer signs may need inversion depending on estimator axis conventions and
  motor rotation direction. This is why motor dry-run, no-prop response, and
  direction tests are mandatory.

Clamping:
  - Disarmed: all motors = 1000 us.
  - Armed idle: all motors = 1050-1100 us after testing ESC start threshold.
  - Active command: clamp to [1000, 2000] us.
  - Test mode: cap to [1000, 1100] us until explicitly expanded.

Desaturation:
  Implement basic clamping first. Add desaturation only after unit tests.

================================================================================
13. ESC OUTPUT DESIGN
================================================================================

Use MCPWM, not Arduino Servo.

Default PWM:
  Frequency = 50 Hz initially.
  Pulse min = 1000 us.
  Pulse max = 2000 us.
  Disarmed = 1000 us.
  Idle = measured ESC start threshold, likely 1050-1100 us.

Boot behavior:
  1. Configure motor GPIOs to safe output state.
  2. Initialize MCPWM with comparator values set to 1000 us.
  3. Only then enable timers.
  4. Never leave ESC signal floating.

ESC calibration:
  Must be explicit, documented, and no-prop.
  Do not run automatic ESC calibration at normal boot.

Motor test mode:
  - from DISARMED only
  - one motor at a time first
  - no-prop confirmation required
  - throttle capped
  - timeout auto-stop
  - ESTOP always active

14. SAFETY STATE MACHINE
================================================================================

States:
  BOOT
  SENSOR_INIT
  SENSOR_CALIBRATION_REQUIRED
  DISARMED
  WIFI_CONFIG
  WIFI_CONTROL_DRY_RUN
  PRE_ARM_CHECK
  ARMED_IDLE
  ACTIVE_STABILIZE
  MOTOR_TEST_MODE
  ESC_CALIBRATION_MODE
  FAILSAFE
  ERROR_LOCKOUT

State output table:

  State                         Motor output              WiFi allowed
  ---------------------------------------------------------------------------
  BOOT                          1000 us                   no
  SENSOR_INIT                   1000 us                   no
  SENSOR_CALIBRATION_REQUIRED   1000 us                   config only if safe
  DISARMED                      1000 us                   yes
  WIFI_CONFIG                   1000 us                   yes, HTTP
  WIFI_CONTROL_DRY_RUN          1000 us forced            yes, UDP test
  PRE_ARM_CHECK                 1000 us                   no HTTP
  ARMED_IDLE                    idle pulse                only if WiFi-control mode approved
  ACTIVE_STABILIZE              mixer output              only experimental UDP, no HTTP
  MOTOR_TEST_MODE               capped test output         yes only if no-prop confirmed
  ESC_CALIBRATION_MODE          calibration pulses         no app except ESTOP
  FAILSAFE                      1000 us                   telemetry only
  ERROR_LOCKOUT                 1000 us                   telemetry only

Pre-arm checks:
  1. MPU6050 detected, WHO_AM_I correct.
  2. Calibration valid.
  3. Gyro bias sane.
  4. Accel magnitude sane.
  5. Board tilt below threshold.
  6. Input source valid.
  7. Throttle low.
  8. Dead-man active if WiFi-control mode.
  9. Explicit arm command.
  10. ESC output initialized.
  11. No critical fault.
  12. No motor test active.
  13. No stale command packets.
  14. Loop timing stable.
  15. WiFi RSSI/packet stability acceptable if WiFi-control mode.
  16. Battery voltage acceptable if voltage sensor exists.

Mandatory disarm/failsafe triggers:
  - ESTOP command.
  - Dead-man release in WiFi-control mode.
  - WiFi packet stale > 150 ms.
  - Receiver stale > 100 ms.
  - IMU persistent failure.
  - Excessive loop overruns.
  - Excessive tilt.
  - Brownout.
  - Control task watchdog timeout.
  - App background/lock event command.
